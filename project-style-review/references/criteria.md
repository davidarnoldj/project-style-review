# Review criteria

## Classify prose by audience

- Write and review first-party developer prose in English. This includes the canonical README, API and module documentation, docstrings, documentation comments, explanatory inline comments (including SQL and configuration comments), design notes, contributor instructions, developer setup and troubleshooting. A German comment beside a German button label requires a different decision from the label.
- Keep the language of deliberate translations such as a maintained `README.de.md` alongside an English original, or a labelled translation paired with a canonical README that itself needs translation. Keep Austrian Standard German in German UI copy, product guides, deliberate German examples and German reports. When filtering to German documentation or UI, select passages by their original language and apply the audience rule to replacements.
- Keep source quotations, third-party text, legal notices, test data, snapshots, exact outputs and machine-consumed comments intact. Distinguish a docstring from a string literal used by the application. Verify any tooling or runtime contract before changing documentation that is used by tooling, introspection or generated API references.

## Technical English

- Check spelling, articles, agreement, prepositions, pronoun references, modifier placement, literal translations from German and consistent technical terminology. Read for comprehension as well as grammar. Prefer direct verbs and name the actor where responsibility matters. Passive voice is useful when the actor is unknown or immaterial.
- Follow the project's established English spelling. Use US English if there is no established variant. Prefer full forms such as “does not” and “cannot” in developer prose. Apply language conventions where they carry meaning. Python function docstrings can open with an imperative summary. Swift documentation can start with a concise summary such as “Returns …” and add contract details when needed.
- Verify disputed claims and proposed technical changes against the implementation, tests or authoritative local documentation. Distinguish a requirement, a recommendation and observed behaviour. Check negation, uncertainty, obligation, conditions, units, counts, bounds, ordering, defaults, side effects and errors. For example, three attempts include the initial attempt, while three retries follow it. If sources disagree, cite both locations and identify the unresolved contract. First-party documentation can establish a precise domain rule even when no matching implementation is visible.
- Preserve identifiers, public API names, commands, flags, placeholders, Markdown link destinations, doctests and machine-readable directives. Recheck the revised passage against the original and the supporting source. In review, quote the passage at its original location and supply usable English wording where the meaning is established. When the meaning is ambiguous, quote it and state the specific question instead of guessing.
- Decide whether a comment earns its place before polishing it. Remove plain narration when the next statement already says it. Retain business rationale, surprising constraints and caller-visible behaviour. Flag a missing explanation when a consequential contract or operational constraint cannot readily be inferred at the point of use. Name the decision it affects and put the explanation where the reader needs it, such as the API declaration, relevant step or constrained branch. If the rationale is unavailable, ask for it. Add documentation for a demonstrated need.

## Code and file layout

- **Reuse.** Inspect both implementations and their callers before proposing reuse. Compare accepted input, normalisation, validation order, error type and timing, output order, mutations, logging, I/O and public import paths. Similar bodies can have different contracts.
- **Indirection and control flow.** Trace wrappers, hooks, options and registries to callers, tests, loaded entry points and configuration. Retain a layer with an independent responsibility. Confirm that early returns preserve evaluation order, cleanup and state changes. Explain the invariant bypassed by a cast or suppression and preserve trust-boundary validation.
- **Failures.** Trace a broad catch or sentinel to its caller and identify the specific failure it hides. Narrowing a catch or adding logging can change observable behaviour. Name the decision needed before editing.
- **Fragmentation.** Inspect neighbouring files before proposing a new file or a move. For code, trace imports (including dynamic use), tests, ownership, public paths, packaging and framework discovery. For documentation, compare each reader's task and inspect anchors, relative links, inbound links and navigation entries. Consolidate when one narrow responsibility is needlessly scattered, or the same reader has competing copies of one procedure.
- **Separation.** File size and count can guide inspection. Keep purposeful boundaries, including package markers, ordered migrations, stable public imports, framework entry points, name-discovered files, localisation resources, separate build targets and filename-sensitive test fixtures. Keep documentation pages with distinct audiences or separately addressable contracts. If external use is unknown, state the evidence gap before proposing removal of a public path. In a file-layout review, briefly name the nearby candidates you considered and would keep separate, with the concrete reason.
- **Consolidation finding.** Give the exact source paths and existing cohesive destination when available. Name what moves, what stays, and the imports, links, anchors, navigation or build references to update. Explain the specific cost saved, such as keeping one procedure current or reading a private policy in one place. A general-purpose utility module or an unrelated README section is rarely a suitable destination.

## Product text in German and English

- Follow the known action or error branch. A cancelled selection and a failed write imply different messages. Preserve accessibility semantics, localisation keys, placeholders, interpolation, pluralisation and argument order. If two guides disagree and the runtime path is missing, keep both steps intact and state what to verify.
- Remove unsupported promises, generic introductions and recaps that give the reader no actionable information. Inspect repetition and punctuation in context. Retain precise technical terms, useful summaries and natural Austrian wording. A word such as “robust” can be precise when the prose names the failure it handles and the resulting behaviour. Leave clear, accurate prose intact when the only alternative is shorter. Replace a vague claim only with an established fact.

## Explicit delivery-leftover check

Inspect the agreed delivery files. Report any pasted chat opener or literal generation notice with its exact text and location. Distinguish first-party delivery prose from a deliberate example, fixture, third-party notice or legitimate attribution. Preserve licences and authorship records. List the files inspected and any requested file that could not be read.
