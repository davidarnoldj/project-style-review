# Review criteria

## Code and comments

- **Reuse.** Find an existing helper and inspect both implementations and their callers. Converging is useful when it prevents a rule from drifting. Check accepted input, normalization, validation order, exceptions and when they occur, ordering of results, mutations, logging, I/O and other observable side effects. A similar body can support different contracts. Preserve public entry points and import paths.
- **Indirection.** Trace a wrapper, unused hook, option or registry to actual callers, tests, package entry points and configuration. A wrapper can carry permissions, a stable interface, an actor boundary or test isolation. Recommend removing a layer only when it has no such responsibility and a concrete call path gets simpler. A search limited to the requested scope cannot prove a public entry point unused.
- **Control flow and types.** Suggest an early return only if it makes the normal path easier to see while retaining evaluation order, cleanup and state updates. For a cast, suppression or broad inferred type, name the invariant being bypassed and a concrete way to express it. Preserve trust-boundary validation and compatibility checks.
- **Failures.** Trace a broad catch or sentinel return to the caller. Report the particular failure it misrepresents or hides. Narrowing a catch, adding logging or changing when an error escapes can change behaviour. Identify that consequence and the decision needed before editing.
- **Comments and docstrings.** Remove narration that repeats a readable operation. Keep constraints, business rules, rationale, examples and non-obvious failure modes. In SQL, a comment just above a predicate can be redundant while a nearby comment on the billing cut-off is essential.
- **Messages.** Follow the error branch to what it establishes. A selector cancellation and a failed write imply different messages. State the failed action or specific reason only if the source knows it. Preserve accessibility semantics, localization keys, placeholders, interpolation, pluralization and argument ordering. Check all affected locales when proposing a functional text change.

## German and English prose

- If two guides or locales disagree about how a feature works, verify the runtime path before suggesting operational wording. A sibling guide can establish a discrepancy. When the relevant source is missing, name the question to verify. Keep both versions intact, including any potentially necessary reader step.
- Read the paragraph and identify the audience and purpose. A technical reference, setup guide, CLI warning and landing page have different jobs. Point to the actual claim, omission, confusing repetition or loss of meaning.
- Treat first-party documentation as evidence for ordinary product instructions and precise domain rules. The absence of a matching implementation in the reviewed files is insufficient to challenge an instruction or rule. Raise a claim when you find counterevidence, an unsupported comparative or empirical promise, or a concrete ambiguity that affects the reader.
- Remove unsupported superlatives and promises or replace them with an already established fact. Delete an introduction or recap if it adds neither orientation nor a next action. A summary that gives a decision, a caveat or a next step earns its place.
- Inspect repeated sentence templates, lists or punctuation when they obscure emphasis or make sections hard to distinguish. A dash or a three-part list in isolation is fine. Preserve the project's English variety, specific terminology and natural Austrian wording. German suggestions and reports use Austrian Standard German, including ß where appropriate.
- Keep exact figures, product names, quotes, code and config literals, glossary meanings and the strength of the original claims. A technical use of “robust” can be precise when the failure covered is stated. A legal or domain-specific term can be more accurate than a plain synonym. Do not add a feature, performance figure or rationale to rescue a vague sentence.

## Explicit delivery-leftover check

Review only the agreed delivery files. If the set is unclear, infer it from the specified deliverable or ask what is shipping. Report an actual pasted chat opener or literal generation notice with its exact text and location. Establish whether it appears as first-party delivery prose, an intentional example, a fixture, a third-party notice or legitimate attribution. Preserve licenses and authorship records. An explicit generation notice can be legitimate disclosure. Report it as such if relevant to the user's request and leave it in place. Do not treat general style as evidence of origin. Include the inspected paths and any excluded or unreadable requested file.
